# peers 방(room) 설계

**날짜**: 2026-09-14
**상태**: 설계 합의 완료, 구현 계획 작성 전

## 문제

지금은 브로커에 붙은 모든 세션이 서로를 봅니다. `list_peers`가 전원을 반환하고 누구에게나 질문할 수 있습니다. 사람이 늘면 목록이 복잡해지고, 한 주제를 두고 오간 질문과 답이 다른 대화들과 섞여 흩어집니다.

**방을 도입하는 목적은 대화 맥락을 묶는 것입니다.** 접근 통제가 아닙니다. 이 구분이 설계 전체를 좌우합니다.

## 결정 사항

논의에서 확정한 것들입니다.

| 결정 | 값 | 이유 |
|---|---|---|
| 목적 | 대화 맥락 묶기 | 보안 경계가 아니므로 멤버 관리·ACL을 만들지 않는다 |
| 방 = | 문자열 하나 | 번호를 알면 입장. 브로커가 멤버 목록을 갖지 않는다 |
| 세션과 방 | 기본은 하나, 이동 가능 | 기동 시 정하고 `join_room`으로 옮길 수 있다 |
| 방 생성 | 강제하지 않음 + 자동 등록 | 첫 입장 시 등록되고 비면 사라진다 |
| 에이전트 생성 | `create_room` 도구 | 세션이 이미 붙어 있으므로 닭-달걀 문제가 없다 |
| 방 미지정 | `public` | 지금 동작 그대로. 기존 사용자는 변경 불필요 |

### 왜 접근 통제로 만들지 않았나

방 번호를 알면 누구나 들어옵니다. 멤버 목록을 강제해도 보호되는 것이 없는데(번호 공유를 막을 방법이 없다) 방 생성·초대·탈퇴 흐름을 전부 만들어야 합니다. 목적이 맥락 묶기이므로 그 비용을 지불하지 않습니다.

**대신 이 점을 문서와 서버 instructions에 명시해야 합니다.** 방이 생기면 "방 안이니 안전하다"고 오해하기 쉽습니다. 이것이 이 설계의 주된 위험입니다.

## 방의 생애

```
create_room 또는 첫 입장
        │
        ▼
   [활성]  ── 사람이 있는 동안 유지
        │
        ├─ create_room 직후 아무도 없음 → 30분 예약, 그 안에 아무도 안 들어오면 소멸
        └─ 마지막 사람이 나감 → 소멸
```

방은 **메모리**에 둡니다. presence와 같은 성격이고, 브로커가 재시작하면 세션들이 다시 붙으면서 복원됩니다. 예약만 재시작에 사라지는데 그동안 아무도 들어오지 않은 방이라 손실이 없습니다.

`create_room`이 예약을 두는 이유는, 예약이 없으면 만들자마자 소멸해 상대가 들어올 때 빈 방을 새로 만드는 꼴이 되기 때문입니다. 예약 시간은 `ROOM_RESERVE_SEC`(기본 1800)로 조정합니다.

### 방 이름

- 사람이 정하는 경우: `[\w.-]{1,64}`
- 브로커가 만드는 경우: `r-` + 6자. 알파벳은 `23456789abcdefghjkmnpqrstuvwxyz` — 헷갈리는 `0/O`, `1/l/I`를 뺐습니다. 읽어서 전달해도 틀리지 않게 하기 위함입니다
- `public`은 예약어입니다. `create_room`으로 만들 수 없습니다

### 주제(subject)

방에 한 줄 설명을 붙입니다. `list_rooms`에 표시되고, **첫 등록자만 설정합니다.** 나중에 들어온 사람이 다른 주제를 적어도 덮어쓰지 않습니다 — 그렇지 않으면 방 설명이 사람마다 바뀝니다.

## 도구

기존 5개에 3개를 더해 8개가 됩니다.

### 새로 추가

**`create_room(subject?, name?)`** — 방을 만들고 이름을 돌려줍니다. **입장하지는 않습니다.**

```json
{ "room": "r-k7m2xq", "subject": "취소 웹훅 중복 수신 조사", "reserved_for_sec": 1800 }
```

| 인자 | |
|---|---|
| `subject` | 방 설명. 최대 200자 |
| `name` | 원하는 이름 직접 지정. 생략 시 브로커가 생성 |

`name`이 이미 존재하면 **409**입니다. **사람이 없고 예약만 걸린 방도 존재하는 것으로 봅니다** — 그렇지 않으면 남의 예약을 덮어씁니다. `public`이면 **400**.

**`join_room(room, subject?)`** — 이 세션을 다른 방으로 옮깁니다.

```json
{ "room": "r-k7m2xq", "subject": "취소 웹훅 중복 수신 조사", "peers": 2 }
```

없는 방이면 그 자리에서 생깁니다(기동 시 `PEERS_ROOM`과 같은 규칙). `join_room("public")`으로 돌아옵니다. 별도의 `leave_room`은 두지 않습니다.

**`list_rooms()`** — 활성 방 목록.

```json
{ "rooms": [
  { "room": "webhook-dup", "subject": "취소 웹훅 중복 수신 조사", "peers": 2, "you": true },
  { "room": "public", "subject": null, "peers": 5, "you": false }
]}
```

**이 도구만 방 경계를 넘습니다.** 방을 찾으려면 방 밖을 봐야 하기 때문입니다. 방이 보안 경계가 아니므로 이름과 주제가 전원에게 보이는 것은 의도된 동작입니다.

### 기존 도구의 변경

| 도구 | 변경 |
|---|---|
| `list_peers` | **같은 방만** 반환. 응답에 `room`, `subject` 추가 |
| `ask_peer` | 후보를 **같은 방으로 제한**. `to` 형식은 그대로. 404의 `available` 목록도 같은 방 기준 |
| `reply` | 변경 없음 — `msg_id`로 배달되므로 방과 무관 |
| `check_inbox` | 변경 없음 — 사용자 단위 복구 경로이므로 방을 적용하지 않는다 |
| `set_status` | 변경 없음 |

`ask_peer`의 `to`를 바꾸지 않는 이유는 방이 암묵적 범위이기 때문입니다. 같은 방 안에서는 지금처럼 `user` 또는 `user@workspace`로 지정하면 충분합니다.

## 방 이동의 의미

**메시지는 방이 아니라 세션(`to_sid`)에 배달됩니다.** 방은 누구를 보고 누구에게 물을 수 있는지만 정합니다. 그래서 방을 옮겨도 이미 라우팅된 메시지는 옮기거나 만료시킬 것이 없습니다.

| 이동 시점에 있던 것 | 어떻게 되나 |
|---|---|
| 나에게 온 열린 질문 | 유지. 새 방에서도 `reply` 가능 |
| 내가 보낸 질문의 답 | 그대로 내 세션에 도착 |
| ack 못 받은 메시지 | 그대로. 재전달 경로는 sid 기준 |
| hops·핑퐁 검사 | sid 기준이라 그대로 동작 |

받은 질문을 들고 방을 옮겨도 답할 수 있게 둡니다. 막으면 질문자만 기다리다 만료됩니다.

`hops`는 방을 넘어서도 누적됩니다. A 방에서 받은 질문 때문에 B 방에서 다시 묻는 것도 재질문이므로, 방으로 제한을 우회할 수 없어야 합니다.

## 데이터 모델

`messages`에 컬럼 하나를 더합니다.

```sql
ALTER TABLE messages ADD COLUMN room TEXT NOT NULL DEFAULT 'public';
CREATE INDEX IF NOT EXISTS idx_room ON messages(room, created_at);
```

**`room`은 보낸 시점의 방이고 이후 바뀌지 않습니다.** 참여자가 나중에 방을 옮겨도 그 대화는 원래 방에 묶인 채로 남습니다. 맥락 묶기가 목적이므로 이것이 맞습니다.

이 컬럼으로 방 단위 감사 질의가 가능해집니다.

```sql
SELECT created_at, kind, from_user, to_user, substr(body,1,80)
FROM messages WHERE room = 'webhook-dup' ORDER BY created_at;
```

방 자체는 메모리에 둡니다.

```python
rooms: dict[str, Room]   # Room = { subject: str | None, reserved_until: int | None }
```

방의 인원은 `sessions`를 세어 구합니다. 별도 카운터를 두지 않습니다 — 두 곳이 갈라지면 반드시 틀립니다.

방은 메모리에 있으므로 무한히 만들 수 있으면 곤란합니다. `create_room`을 기존 rate limit 창(10분)에 태우고, **한 사용자가 동시에 예약해 둘 수 있는 빈 방을 5개로 제한**합니다(`MAX_RESERVED_PER_USER`). 초과하면 429입니다. 사람이 들어찬 방은 이 한도에 세지 않습니다.

## 설정

```bash
PEERS_ROOM=webhook-dup PEERS_ROOM_SUBJECT="취소 웹훅 중복 수신 조사" \
  PEERS_LISTEN=1 claude --channels plugin:peers@claude-peers
```

| 우선순위 | 출처 |
|---|---|
| 1 | `PEERS_ROOM` 환경변수 |
| 2 | `default_room` (플러그인 userConfig, 선택) |
| 3 | `public` |

`PEERS_ROOM_SUBJECT`는 그 방의 첫 등록자일 때만 반영됩니다.

`plugin.json`에 `default_room`(선택, non-sensitive)과 `PEERS_ROOM`/`PEERS_ROOM_SUBJECT` 환경변수 통과를 추가합니다.

## 브로커 API

| 엔드포인트 | 변경 |
|---|---|
| `GET /api/peers` | 같은 방만 반환 |
| `POST /api/ask` | 같은 방으로 후보 제한 |
| `POST /api/rooms` | **신규** — `create_room` |
| `POST /api/rooms/join` | **신규** — `join_room` |
| `GET /api/rooms` | **신규** — `list_rooms` |
| `GET /healthz` | `rooms` 개수 추가 |

WebSocket 연결 시 `x-peers-room`, `x-peers-room-subject` 헤더를 받습니다. 워크스페이스와 같은 방식으로 검증하고, 형식이 어긋나면 `public`으로 떨어뜨립니다.

## 기존 사용자와의 호환

`PEERS_ROOM` 없이 띄우면 `public`입니다. **지금 동작과 같습니다.** 기존 설치자는 아무것도 하지 않아도 됩니다.

`ALTER TABLE`의 `DEFAULT 'public'` 덕분에 기존 메시지도 전부 `public`에 들어갑니다. 마이그레이션 스크립트가 필요 없고, 기동 시 컬럼 존재 여부를 확인해 없으면 추가합니다.

구버전 채널 서버가 새 브로커에 붙으면 `x-peers-room` 헤더가 없으므로 `public`이 됩니다. 반대로 새 채널 서버가 구버전 브로커에 붙으면 방 관련 도구가 404를 받습니다 — 도구 설명에 브로커 버전이 낮을 수 있다고 적어 둡니다.

## 테스트

E2E에 추가할 시나리오입니다.

1. 방이 다른 세션은 `list_peers`에 보이지 않는다
2. 방이 다른 세션에는 질문할 수 없다 (404, `available`도 같은 방 기준)
3. `create_room`이 이름을 돌려주고, 아무도 없어도 `list_rooms`에 뜬다
4. 이름 충돌 409, `public` 생성 400
5. `join_room`으로 옮기면 그 방 사람이 보인다
6. **방을 옮겨도 이전 방에서 받은 질문에 `reply`할 수 있다**
7. `messages.room`이 보낸 시점 값으로 고정된다 (옮긴 뒤에도 이전 대화는 이전 방)
8. `PEERS_ROOM` 없이 뜬 세션은 `public`이고 기존 동작이 그대로다
9. `subject`는 첫 등록자만 설정한다
10. hops는 방을 넘어서도 누적된다

## 범위 밖

- 방 멤버 관리·초대·비밀번호 — 접근 통제가 목적이 아니다
- 방 이름 영구 등록(재시작 후 유지) — 사람이 있는 동안만 존재하면 충분하다
- **질문** 빈도를 방 단위로 세는 것 — 지금의 사용자·상대 기준으로 충분하다 (방 **생성** 제한은 위에 있는 대로 넣는다)
- 방 이동 시 동료에게 알림 — 필요해지면 그때
- `subject` 수정 — 첫 등록자 고정으로 시작한다

## 남는 위험

**방을 격리로 오해하는 것.** 이 설계에서 가장 실제적인 위험입니다. 완화책은 세 곳에 명시하는 것입니다.

1. 서버 `instructions` — Claude가 방을 근거로 민감한 내용을 공유하지 않도록
2. `create_room` / `join_room` 도구 설명
3. USAGE.md

문구는 "방은 대화를 묶는 수단이고 접근 통제가 아닙니다. 번호를 아는 사람은 누구나 들어올 수 있고, 방 이름과 주제는 전원에게 보입니다."
